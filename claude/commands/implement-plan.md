## Task

Execute a plan produced by `/fable-plan` in a cheaper-model session. The plan is the authority; this session contributes labor, not judgment. A short plan (its header line says `Short plan:`) hands local judgment back: decide where it is silent, never where it has decided, and list each choice in the PR body.

Resolve the plan file from `$ARGUMENTS`, after removing the skip token: the word `--no-self-review` wherever it stands as a word of its own. claudeos sends it for an implement launched with `--self-review no`, whose PR a separate review job takes (steps 5 and 6). Arguments that held only the token are the empty form. Remove the base pair the same way: the word `--base` wherever it stands as a word of its own, and the word after it, which names the base branch (see **Base branch**). Arguments that held only the pair, or only the pair and the skip token, are the empty form.

- **Queue form** — `<project> | <item>`: resolve the line with `claudeos queue find <project> <item>` (`qN` ID, `#issue` ref, or text fragment; the vault is `~/obsidian/SecondBrain`, reachable from any cwd) and follow the result's `plan` wikilink to `projects/<project>/plans/`. If the line has no `→plan:`, stop and tell the user to run `/fable-plan <project> | qN` first.
- **Path form** — a file path, read as given.
- **Empty** — use the newest file in `docs/plans/`; if none exists, stop and tell the user to run `/fable-plan` first.

## Base branch

claudeos sends `--base <branch>` for an implement launched with `--base`: the work builds on a branch that has not reached the default branch yet (a stacked PR), so it starts from that branch and its PR targets it. Below, `<base>` is that branch name and `<default>` the default branch's name. With no pair in `$ARGUMENTS` this section does not apply and every step reads as if it were not here.

**The name.** `<base>` is a bare branch name on `origin` (`q806-review-kind-on-the-cli`, never `origin/q806-review-kind-on-the-cli`). Check it as text before any command carries it: at most 200 characters, made only of `A-Z`, `a-z`, `0-9`, `.`, `_`, `/` and `-`, not starting with `-`, holding no `..`, and with no `/`-separated part that is empty, starts or ends with `.`, or ends with `.lock`. A name that fails, a `--base` with no word after it and a second `--base` are each a stop-and-ask (step 3) before `queue find` or any git command runs: never repair the name and never guess one. The name is then written into a command in four places only: as `refs/heads/<base>` for `git ls-remote`, as `origin/<base>` for `git switch -c` and `git merge`, and as the value of `gh pr list --head` and of `gh pr create --base`. This command never pushes to the base, never deletes it and never checks it out.

**Its state.** Read it twice: in step 2, after `git fetch origin` and before the plan's branch is created or checked out, and again in step 4, before the merge (before the push, when the merge is skipped). Each read is these three commands, one plain call each; one that errors is a stop-and-ask:

- `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` prints `<default>`.
- `git ls-remote origin refs/heads/<base>` prints one line when the branch is on origin and nothing when it is not.
- `gh pr list --head <base> --state all --json number,state,baseRefName,isCrossRepository` lists the PRs opened from a branch of that name, newest first. Ignore every entry whose `isCrossRepository` is `true`: a fork's branch of the same name is another branch.

The first row that fits, top to bottom, is the state:

| What the read shows | State |
|---|---|
| `<base>` is `<default>` | **no base**: go on as if the pair were absent |
| an entry has `state` `OPEN` (take the first one), and the branch is on origin | **stacked** on that PR, `#<number>` |
| no `OPEN` entry, and the first `MERGED` entry has `baseRefName` `<default>` | **landed**: the base's work is on the default branch |
| no entry, and the branch is on origin | **stacked**, on a branch with no PR yet |
| anything else | stop-and-ask (step 3), printing the three outputs |

"Anything else" is an `OPEN` entry whose branch is gone from origin, a first `MERGED` entry whose `baseRefName` is another branch (the base's work is not on the default branch, and this command does not guess where it went), entries that are all `CLOSED`, and no entry with no branch. A merged branch often stays on origin, and a squash merge leaves it no ancestor of the default branch, so neither the branch's presence nor `git merge-base` is read as merged; the PR's state is.

**Stacked, in step 2.** A plan branch that does not exist yet is created from the base, `git switch -c <name> --no-track origin/<base>`, in a linked worktree or not, in place of both creations step 2 describes. A plan branch that already exists is checked out as step 2 says and then, in a linked worktree, `git merge origin/<base>` runs before any task does, with step 4's rules for a conflict and for failing checks, so fixes that landed on the base since the last session are under the work. A plan check that compares against the default branch (`git diff --stat origin/master`, "names only these files") is run against `origin/<base>` instead, since the default branch lacks the base's commits.

**Stacked, in step 4.** The merge that brings the branch up to date is `git merge origin/<base>` in place of the default branch's, under the same linked-worktree condition and the same conflict rules; never merge the default branch into a stacked branch, which would put its commits in the PR's diff. The PR is opened with `gh pr create --assignee @me --base <base>`. The PR body's second line, right under the `Closes` or `Plan:` line, is `Stacked on #<number> (<base>): merge #<number> first, then retarget this PR to <default> before merging it.`, or, for a base with no PR, `Stacked on <base>, which has no PR yet: retarget this PR to <default> once <base> has landed there, before merging it.` The body's `## Post-deploy` section gains as its first line (replacing a `- none`) `- [ ] run: before the merge, look at this PR's base. While it is <base>, merge <base>'s own PR first, then run gh pr edit <this PR's number> --base <default> in your own shell, wait for the checks, and only then merge. Merged into <base> after <base> has landed, this PR's work never reaches <default>.` This session does not retarget a PR on its own.

**Landed.** Every step reads as written: the plan's branch starts from the default branch (step 2), the default branch is merged (step 4) and the PR targets it. A branch that was stacked in step 2 and whose base has landed by step 4 is handled the same way, and step 4's merge of the default branch is what brings the landed base's commits under it. In both cases the PR body's second line is `<base> landed on <default> before this PR opened; it targets <default>.`

**A plan that stacks itself.** A plan may name, in its own first task, the branch its work starts from and the branch its PR targets. It is followed as written when it names the same branch as the pair, and is a stop-and-ask when it names another.

## Steps

1. **Load the plan.** Read it fully, including its stop-and-ask list. This command's steps are the checkpoint discipline; the repo's harness skill, when its `CLAUDE.md` names one (claudeos: `claudeos-workflow`), is how each phase's code gets written and verified. No other execution skill is invoked. A ticked box (`- [x]`) is a task an earlier session finished, committed and pushed, possibly on another machine; the plan file is the progress record a handoff reads. Treat those tasks as done and start at the first task with an open box, once the checkout is on the plan's branch with those commits in `git log --oneline` (step 3 stops otherwise). When the plan's frontmatter carries `repo:`, compare it now with this checkout's origin (`git remote get-url origin`, cut down to `owner/name`, case ignored): a different repo means the session was launched in the wrong checkout, and step 3 stops before anything is touched.

2. **Implement.** First check for a worktree: if `git rev-parse --git-dir` and `git rev-parse --git-common-dir` differ, the session is in a linked worktree - do all work inside it (root: `git rev-parse --show-toplevel`) and never touch the main checkout. The worktree guard refuses compound shell, so write every command as one plain call: no `&&`, `;` or pipe chaining git with anything else, no `cd` prefix, no `git -C`, no heredoc, and no runtime-built value (`$TMPDIR`, a `$(...)` argument, `awk -v`). Write multi-line edit scripts, probe scripts and the PR body to files in the session's scratchpad directory and pass them by absolute path (the PR body through `gh pr create --body-file <path>`). Put the same rule in every agent brief you write (feature-dev, qa-verifier, any other), since those agents never read this file. Then get on the plan's branch, whose name is fixed: the plan file's stem without its date, prefixed with `q<N>-` for a queue plan (`2026-09-14-implement-plan-ticks-boxes.md` for `^q197` is `q197-implement-plan-ticks-boxes`). The `worktree-*` branch Claude Code created for the session is never the plan's branch. Run `git fetch origin` (then, with a base pair in `$ARGUMENTS`, read the base's state as **Base branch** says), then `git ls-remote --heads origin '<name>*'` with the `q<N>-` prefix alone as the pattern for a queue plan: exactly one ref is the item's branch, possibly pushed from another machine, so check it out instead of creating one (`git switch <branch>` then `git pull --ff-only` when a local branch of that name exists, else `git switch -c <branch> --track origin/<branch>`; stacked on a base, then merge the base as **Base branch** says); no ref means create it (stacked on a base: from `origin/<base>` as **Base branch** says, in place of the two creations that follow): in a linked worktree from the latest default branch, whose name `git symbolic-ref --short refs/remotes/origin/HEAD` prints (`origin/master`), with `git switch -c <name> --no-track <that name>`, so the work starts from what is merged and not from where the main checkout's HEAD stood, and from the current HEAD with `git switch -c <name>` when that command prints nothing or the session is not in a linked worktree; two or more refs is a stop-and-ask. In a linked worktree, install dependencies before the first test, check, commit or merge, since a fresh worktree has no `node_modules` and the pre-commit hook would run without its tooling: run `git ls-files 'yarn.lock' '*/yarn.lock' 'package-lock.json' '*/package-lock.json' 'pnpm-lock.yaml' '*/pnpm-lock.yaml'`, and for each lockfile whose directory has a `node_modules` in the main checkout (the parent of `git rev-parse --git-common-dir`, read only, checked with `ls`) but not in the worktree, run that manager's frozen install on the worktree directory, one plain call each with a literal absolute path: `yarn --cwd <dir> install --frozen-lockfile` (`corepack yarn` when `yarn` is not on PATH), `npm ci --prefix <dir>`, `pnpm --dir <dir> install --frozen-lockfile`. A directory with no `node_modules` in the main checkout is skipped, so a repo with no installed dependencies (claudeos) installs nothing. Follow the plan exactly, phase by phase. For each phase (a `### Task N` heading in the plan), in this order: run its verbatim check commands and compare against the plan's expected results, or, when the phase names no commands, run the tests it names and the repo's gate (`make check`, or whatever the repo's `CLAUDE.md` names) and compare against the plan's **Acceptance** block; commit using the repo's commit conventions; `git push -u origin HEAD`; then tick the phase in the plan file, turning every `- [ ]` under that heading into `- [x]`, in the file where the plan lives (the vault for a queue plan, `docs/plans/` for a path plan; never commit it). Only then move on. The push is what lets another machine check the branch out; the ticks are what tell it where to resume.

3. **Stop and ask** the moment any trigger fires - the plan's own stop-and-ask list plus these defaults:
   - Reality deviates from the plan (file moved, API changed, signature mismatch).
   - Tests still failing after 2 fix attempts.
   - An ambiguous requirement surfaces mid-phase.
   - A security-sensitive decision (auth, access scoping, user input, secrets) is not spelled out in the plan.
   - The branch lookup in step 2 cannot land on one branch: `ls-remote` lists two or more refs, `git switch` refuses (a dirty tree, or the branch is checked out in another worktree on this machine), `git pull --ff-only` refuses, or the plan has ticked boxes and origin has no branch for it (a tick is written only after a push, so the vault and origin disagree).
   - A dependency install in step 2 fails, or leaves a lockfile modified in `git status`. Never commit the lockfile change: it is a dependency change the plan did not ask for.
   - The plan's `repo:` is not this checkout's origin (step 1). Name both repos and stop: the fix is a relaunch in the right checkout (in claudeos, the launch overlay's `repo:` field), never an edit of the other repo from here.
   - The base pair fails its name check, a base-state command errors, or the state is none of the four **Base branch** names, at step 2 or at step 4. Print the name and what the three commands printed, and stop: never branch from, merge or target a branch the table did not settle. A plan that stacks itself on another branch than the pair names stops here too.

   When stopping: summarize state (phase, what fired, options), then wait. Do not improvise a resolution.

4. **Open the PR** once all phases pass their checks. First, in a linked worktree, bring the branch up to date: `git fetch origin`, then `git symbolic-ref --short refs/remotes/origin/HEAD` for the default branch's name (`origin/master`), then `git merge <that name>` (with a base pair, read the base's state again first, and while it is stacked merge `origin/<base>` in its place, as **Base branch** says); when the session is not in a linked worktree or that command prints nothing, skip the merge and say so in the PR body; on a conflict keep what both sides meant, rerun the plan's checks for the files the conflict touched and the repo's gate, and commit the merge; a merge whose checks still fail after 2 fix attempts is a stop-and-ask (step 3), and `Already up to date` needs nothing. Then consult the advisor, when the `advisor` tool is among this session's tools (no tool, no consult): it reads the whole transcript, so say in a line or two what the PR body is about to claim (the checks run, and each review the repo's Definition of Done asks of this diff, as run or as skipped and why), then call it. Do what it finds owed before the PR exists, so the body is written once and step 5 reviews claims that hold; advice that would change the plan's approach is a stop-and-ask (step 3), not a rewrite. Then push the branch, then `gh pr create --assignee @me` (with `--base <base>` while stacked on a base; derive repo from `git remote get-url origin`; no Claude attribution in the description). PR body, in this order: first line exactly `Closes <project> ^qN.` when the plan came from a queue (this line is what `claudeos sync` matches, so it is required, not optional; a plain-form plan writes `Plan: docs/plans/<file>` instead); then, with a base pair, the second line **Base branch** gives for the base's state; then the plan summary; then the per-phase checklist of what was verified; then, for a short plan, a `Local choices:` list of every decision the plan left to you; then the plan's `## Post-deploy` section, heading and lines, copied from the plan and brought up to date with what the run learned: a line whose fact changed is rewritten, a step the run found necessary is added, and a line that no longer applies stays as `- [x] dropped: <why>`, never deleted; a `- none` is copied as is unless the run found a step, in which case the lines replace it; a plan with no such section (written before 2026-10-06) gets the heading with `- none`, or with the lines the run found; then `Plan: projects/<project>/plans/<file>.md (vault)`.

   If the plan came from a queue (queue form, or a plan whose frontmatter carries `queue:`/`queue_item:`), run `claudeos queue mark <project> <qN> --pr <url>` and `claudeos queue state <project> <qN> wip`. The queue should show in-flight work without waiting for a reconcile.

5. **Run `/review-pr --apply --watch`** on the new PR. Its analysis verdicts gate what gets applied; its termination rules end the watch. A `Needs clarification` verdict is a stop-and-ask trigger, not something to guess through.

   With the skip token `--no-self-review` in `$ARGUMENTS`, step 5 does not run at all and nothing in this session reviews the PR: a separate review job takes it. Go to step 6 once step 4 has opened the PR and, for a queue plan, run its `queue mark --pr` and `queue state wip`.

6. **Record, report and stop.** Once step 5's watch has ended, and not before (with the skip token `--no-self-review`, once step 4 is done, since step 5 does not run), name the run's friction: one sentence, either one instruction this run was missing (something you had to work out, guess or stop to ask because the plan, this command or the repo's harness did not say it) or one manual step you repeated that a rule or a script would remove. Name the one that cost the most, the sentence the repo's harness handed with the qa values (claudeos: `claudeos-workflow` Phase 4, which already picked over its agents' `Friction:` lines) weighed beside your own; when nothing qualifies the friction is `none`, never filler.

   Then collect the run's leftovers: the `Leftovers:` line of step 5's review summary plus anything the run itself leaves pending (with the skip token there is no review summary, so the leftovers come from the run alone). Apply the global Leftovers rule from `~/.claude/CLAUDE.md` to each (offer when attended, register when `CLAUDEOS_JOB_ID` is set). This comes before the record, which ends a chained session.

   Then record the run's outcome: `claudeos record`, plus `--qa <pass|fail> --blockers <N>` when the repo's harness ran a verifier (the times the run stopped to ask are counted by claudeos's Stop hook, not reported), plus `--friction "<the sentence>"` unless it is `none`. A refused record answers on stderr and writes nothing: on `flag provided but not defined: -friction` (an older claudeos) run the same record again without `--friction`; on any other refusal fix the argument and run it again. It is a no-op outside a claudeos-launched session; skip it when `claudeos` is not on PATH. This record is what tells claudeos the session is finished, and a chained implement is ended on it, so it never runs while the review watch is still live. Final summary: phases completed, checks run, review threads resolved (with the skip token, `Review: left to a separate job` in their place), PR URL (for a PR opened with `--base <base>`, followed by `stacked on <base>: retarget to <default> before merging`), then `Friction: <the sentence, or none>`, then `Leftovers: <the fN list, the offers, or none>`. Suggest a Fable review pass (`/code-review <pr>`) as the closing step.

## Rules

- The plan outranks your preferences. Disagree with an approach? That's a stop-and-ask, not a silent rewrite.
- No scope beyond the plan: no drive-by refactors, no extra features.
- Before changing a function's signature, return value or exported name, or deleting a symbol, find its uses as `~/.claude/docs/lsp-blast-radius.md` says. A use the plan does not name is the "Reality deviates from the plan" trigger.
